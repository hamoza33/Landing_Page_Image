# SPA dashboard and sequential image generation

Two changes ship together: a single-page admin dashboard replacing the multi-page flow (login → dashboard → jobs), and a rewrite of the image generation pipeline from parallel to sequential with continuity crops and Arabic text embedding. The SPA uses vanilla JS with section show/hide driven by sidebar navigation, talking to new JSON API endpoints (`/admin/api/status`, `/admin/api/jobs`). The image generator now loops through sections one by one, passing a 200px bottom crop of each completed section as a reference image to the next, and injects the actual Arabic copy text into every prompt.

**Watch for:** API credentials (Yunwu key, Google Vision key) are rendered into the HTML served at `/` without any authentication gate — anyone who can reach the server can view them in page source (confirmed). The `STEP_PROGRESS` mapping no longer matches the actual progress strings emitted by sequential generation, so the jobs API will report 50% for all image-generation sub-steps (confirmed).

## High-level view

The SPA collapses login, generation, jobs history, and settings into one template that starts hidden behind a JS-driven auth check against `/admin/api/status`. The server-side route at `GET /` passes all settings — including API secrets — into the template context before the browser decides whether to show or hide the UI. This is a hard credential exposure for any deployment reachable on a network.

Sequential generation replaces the semaphore-gated parallel loop. Each section's normalized output is bottom-cropped (200px) and forwarded to the next call as a continuity reference. Sections in `PRODUCT_REF_SECTIONS` also receive the original product photo. The 8× serial latency is now the pipeline's critical path with no cancellation or timeout at the individual-section level.

Progress reporting was updated in `pipeline.py` to emit per-section messages like `"generating section 3 of 8: before_after"`, but the `STEP_PROGRESS` dict in `main.py` still maps the old `"generating 8 section images"` string. The `.get(step, 50)` fallback hides the mismatch — the jobs API and SPA progress bar will show a flat 50% throughout the entire image generation phase.

## Credential exposure via server-rendered template

The root handler loads `all_settings = load_settings()` and passes the entire dict into the Jinja2 context. The template binds it into form fields:

```html
<input type="password" id="yunwu_api_key" value="{{ settings.api.yunwu_api_key }}" />
```

`type="password"` hides the value visually but it's present in the DOM/source. Before this change, the index route only passed `show_api_icons` — no secrets. The SPA JS hides the `#app-section` div until `/admin/api/status` confirms authentication, but the HTML is already delivered. Any HTTP client (or View Source) exposes the keys.

The fix is to not pass secrets in the initial render. Let the SPA fetch settings from an authenticated endpoint (`/admin/api/settings`) after login succeeds, and populate the form client-side.

## Progress mapping drift

`pipeline.py` now sets the initial step to `"generating section 1 of 8: hero"` and then the `ImageGenerator.generate_all` callback fires `"generating section N of 8: key"` for each subsequent section. The `STEP_PROGRESS` dict:

```python
STEP_PROGRESS = {
    "queued": 5,
    "analyzing product image": 15,
    "generating Arabic copy": 35,
    "generating 8 section images": 55,  # never matched
    "stitching final long image": 85,
    "complete": 100,
}
```

None of the new strings match. The dict's `.get(step, 50)` returns 50 for all eight calls. In the SPA, the `STEP_ESTIMATES` JS object has the same stale mapping, so the progress bar jumps from 35% (copy generation) to a flat 50% until stitching starts. To fix: either use a prefix match (startswith), or map each `"generating section N..."` string, or have the pipeline emit a numeric progress value alongside the text.

## Sequential generation latency and failure isolation

The old code ran 8 image calls in parallel under a semaphore (default concurrency 3). The new code is fully serial: each section awaits its API response before starting the next. For a typical 15–30 second image generation call, total wall-clock time goes from ~45s (3-way parallelism) to ~2–4 minutes.

There's no timeout on individual section calls beyond the 120s `httpx` timeout buried in `YunwuClient`. If the API is slow but not timing out, the user waits silently. More importantly, there's no mechanism to abort a job mid-pipeline — the `BackgroundTasks` runner doesn't expose cancellation.

A partial mitigation: wrap `_call_image_api` in `asyncio.wait_for(coro, timeout=settings.section_timeout)` and surface which section failed.

## Prompt construction: no double-quote enforcement at runtime

The tests assert that prompts contain no double-quote characters. The implementation achieves this by rewriting scene descriptions that previously used `\"...\"`-style quoting into dash-separated phrasing. One edge case: the Arabic copy text itself (headlines, body text, testimonial quotes) is interpolated directly via f-strings. If the LLM-generated Arabic copy contains double-quote characters (possible in Arabic/English mixed text), the prompt will contain unescaped quotes. The constraint is enforced at test time with fixed fixture data but not at generation time — consider stripping or replacing `"` in the `_get_section_arabic_text` return value.

## XSS in jobs table rendering

The JavaScript renders the jobs table via `innerHTML`:

```javascript
html += '<span class="error-text">' + job.error.substring(0, 80) + '</span>';
```

`job.error` is derived from Python exception `str(exc)`. The `generate-url` endpoint accepts an arbitrary URL; if that URL contains HTML/script fragments, the resulting exception message (`"Failed to download image: ..."`) could carry them into the DOM. Using `textContent` on a created element, or escaping the string, closes this.
